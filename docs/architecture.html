One engine, three deciders

A tool author writes a plain function. Everything that makes a call durable, approvable, retryable or budgeted happens somewhere else — and that somewhere is one component.

Green is built and tested — a caller names a tool and gets an answer through every green box, a run is durable in the store and its events reach a subscriber live and from the record. Terracotta is next: the authority model. Dashed is designed and deliberately not built, because in this repository a field arrives when the thing that enforces it arrives.

Solid is a call, dotted is a record, dashed is loaded or derived

the thing to read off the map

A tool handler is a plain function. It never learns a human was asked.

Three requirements arrived together: approval may apply to any call, both decider kinds are durable, and a tool author implements an interface and nothing else. Only one arrangement satisfies all three — asynchrony is imposed on a tool, never implemented by one.

freeze_account is declared async and its handler is an ordinary synchronous function. rund creates the run, waits for a person, then makes the call on the right of the map. The alternative puts a database in every tool service.

Who is in the path, and when

rund is in the path of every call. A decider that is a loop appears only when the thing invoked is an agent — so async does not imply a decider.

Adding an agent deploys nothing. A decider is parameterised by the agent's declaration — prompt, allowlist, step limit — so one ReAct service answers every ReAct agent in the estate. That is the payoff for addressing deciders by kind rather than at each agent's own subject.

The last row is a contradiction, not merely unwise: both decider kinds are durable by definition, so an agent can never complete inside a call. Refused by garmctl compose.

sync is a safety claim, not a speed one

freeze_account takes milliseconds and is async. list_payments pages a ledger for ten seconds and is sync. The axis is whether state outlives the call.

Declaring sync forbids interposing a human

Without that, a deployment's approval policy could turn a truthful budget: 2s into four hours with the author doing nothing wrong. So the declaration is a constraint on policy, which is what keeps the budget honest — and it is the named enforcer for “some tools must never allow a human in the loop”.

The budget binds in three places

The generated client uses it as the deadline, so no caller invents a number. The tool's transport cancels past it, because the caller has already given up. And compose refuses an agent whose budget is below the largest in its allowlist — the max, not the sum, because summing needs to know whether calls are sequential, and nothing knows that until something orders them.

Why one engine and not a decider per call

Retries, guardrails and budgets are needed by every call — which refutes an earlier draft of this design that claimed a plain tool call has no state machine. It has one the moment retries exist: attempt 1 fails UNAVAILABLE, wait, attempt 2.

But “decider” was doing two jobs. The engine — retries, guardrails, budget accounting, approval, state, the tree, the event stream — is needed by everything, and it is rund. A decider only answers “what next”, and only a multi-step program has one.

An earlier version of this page got the next bit wrong

It said a decider must therefore be a pure reducer, because otherwise each kind would carry its own guardrails, retries and budget accounting and they would diverge. That is false. A decider's tool calls go back through rund, so rund applies all three whoever started the call. Nothing was ever duplicated. Asking how DBOS and Temporal would both be deployed is what exposed it.

What a decider actually owns is only its own orchestration position — which is exactly what DBOS and Temporal exist to own. So a decider may keep durable state of its own, or be a reducer whose state rund checkpoints. One Report channel serves both, and the interface does not have to choose.

rund has no such choice. A single-step async call has no decider in its path at all, so there is nobody else to hold the run. That is why rund uses DBOS, behind a narrow port — with Postgres on the asynchronous path and nothing whatsoever on the synchronous one.

A run is a tree

A decider calls tools through rund, and a nested call may itself need approval. So it needs its own state, which means its own run.

r1  assist.v1.payment_triage        correlation c1 · no parent
├── r2  payments.v1.get_balance     correlation c1 · parent r1
└── r3  payments.v1.list_payments   correlation c1 · parent r1

One correlation id across the whole tree; causation ids are its edges. Three things follow: a nested call gets its own approval state, the allowlist is checked per nested call at call time, and this is the real reason a run id comes back even from a synchronous call. The cost is real — a ReAct agent making eight calls is nine runs.

tasksd dissolving is the clearest win: once runs are durable, “waiting for a person” is a state, not a subsystem.

But that estate's constraint was emphatic, and it was not arbitrary

garmd was to have no database access at all. rund takes its job and agentd's store, so a component in the hot path of every call now has a database dependency, and the blast radius of the thing every caller talks to has grown.

Un-collapsing is not the answer — that split cost a ten-step chain between an agent and a tool, four bugs in series on one endpoint each masking the next, and a day to get the plane back. So instead: collapse the contract, keep the store boundary crossable. The split falls along the sync/async line for free, which turns it into a testable claim rather than an intention — a sync call touches no store, which is the dotted line on the map that stops short.

What a caller knows: a name, and nothing else

client := paymentsv1.NewPaymentsClient(rund)

bal, err := client.GetBalance(ctx, &GetBalanceRequest{AccountId: "a-1"})
// sync  -> (*GetBalanceResponse, error).  Deadline is the DECLARED 2s.

ref, err := client.FreezeAccount(ctx, &FreezeAccountRequest{…})
// async -> (*run.Ref, error).  A DIFFERENT SIGNATURE, from the declaration.
res, err := ref.Await(ctx)
// the caller's own patience. Giving up does NOT cancel the run.

No subject, no decider, no decider kind. And flipping a tool from sync to async makes every caller fail to compile — the same discipline as the handler interface having no Unimplemented embed. The alternative is a caller waiting forever for an answer that has quietly become a receipt.
