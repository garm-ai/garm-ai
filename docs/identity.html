One token, three origins

Whether one identity model can carry a human at a keyboard, an agent running at 03:00 with nobody present, and a batch job that answers to no person at all.

The short answer is that two of the three are designed and one is explicitly out of scope — and the one that is missing is the one that looks easiest. What follows is why, what the mechanism actually is, and the four gaps worth knowing before anything gets built.

A user at a keyboard

Covered

Live token exchange. Their own identity provider token is verified, their authority folded, and a short-lived call token minted. The human is present, so nothing has to outlive them.

An agent, for a person

Covered · the hard case

A standing grant holds the person's authority as a signed snapshot. At 03:00 the run needs neither a token of theirs nor an authority lookup. This is the case the design was written for.

Service to service

Not covered

A batch job that is the principal has no consenting person, so there is no grant and no ceiling. The spec names this and declines it: "an agent that must act for nobody is a different design."

The constraint that shapes everything

Before any of this: a NATS message does not say who sent it. The Msg struct carries a subject, a reply subject, headers and bytes. There is no client info, no authenticated-user field, nothing. I read the struct rather than assuming it, because the whole design rests on it.

So identity has to be made visible deliberately. There are exactly three ways, and they are not equivalent:

MechanismWhat it provesCost
in the subject Unforgeable. The server refuses a publish on a subject that is not yours, so the subject is the identity claim A credential and a subject per caller; the subject space grows
in a signed token Cryptographic. Forgeable only by whoever holds the signing key A verifier, a JWKS cache, clock skew, key rotation, revocation
asserted in a header Nothing, on its own. It is worth exactly what the right to publish on that subject is worth None — which is the problem

The third is not useless; it is the second collapsed into the first. A header is trustworthy precisely when a subject permission makes it so, and never on its own merits.

NATS supplies the first one properly verified

Two features matter, and together they remove the need to trust any caller.

Auth callout hands the connection decision to a service you run. The server packages what the client presented and asks for a verdict; the service replies with a signed user JWT that places the client in an account. So the same service that issues application identity can issue transport identity — one identity system, not two bolted together.

account_token_position is the sharper one. On a cross-account service export, NATS guarantees the account key on the subject belongs to the account doing the import. The caller's identity arrives in the subject, placed there by the server rather than by the caller. That is server-enforced, unforgeable caller identity — and it is what makes the binding check in the next section possible at all.

Three objects, not one

The reflex when a run outlives a session is to lengthen the token. That is the wrong move, and the design does the opposite: it makes the token shorter and moves durability into a different object.

1 · The consent template designed

Ships with the agent, in its declaration. What it will ask for: description, scope, default period, default limits, which triggers.

Nothing is hand-written per agent. The consent screen is rendered from the catalogue, and the template's defaults are maxima — a person may tighten them and is never offered the chance to loosen them.

2 · The standing grant designed

A signed document, minted once when the person consents, stored in the token service's own database. It is never sent anywhere — it is cited by id, and the service reads it from its own store.

This is the durable object. Revocable, countable, auditable.

3 · The per-call token designed

Minted at use, lives for minutes, bound to whoever presents it. Nothing holds one; it is re-minted whenever the engine needs to act.

Its short life is the revocation window. A long token would make revocation meaningless.

Why 03:00 works

The grant carries a ceiling: the person's folded authority on the day they consented, carried forward signed. That one idea is what removes both problems at once — the run needs no token of theirs, and no authority lookup either. The ceiling can only ever shrink: a change that narrows their authority narrows every later run, and one that would widen it changes nothing.

the per-call token, minted at 03:00 on a Sunday

sub   = customer:cust_ab12cd        whose authority this is
act   = [agent:weekly-digest]       who is acting — a chain, not a name
exec  = runner:rund                 which process is carrying it
grant = grt_01j…                    which standing grant authorised this
cnf   = { sub: runner:rund }       bound to the presenter — cannot be lifted
exp   = now + minutes               the revocation window
garm  = scope ∩ manifest ∩ ceiling  the fold

Three nested narrowings in that last line. The person's consent (scope), the agent's current release (manifest, read now — so narrowing an agent narrows runs already granted), and the person's authority at consent (ceiling). Whichever is tightest wins.

Why cnf matters more here than anywhere else

An agent is driven by a model. Without presenter binding, a decider that got hold of a token could act as the person on its own account. cnf names the process the token was minted for, and the receiver refuses a token presented by anything else — "presented by a workload it was not minted for."

It is also the architectural reason the standing rule holds: the token is attached by the engine's own call path, below anything a model can influence. A model cannot set it for the same reason it cannot set an idempotency key.

One token, three origins

Here is the claim worth testing, because if it holds the model is simple and if it fails the model is three models: all three callers produce the same token shape. They differ only in where authority came from, and the engine treats what arrives identically.

The three traces

Frame by frame, so the differences are concrete rather than asserted.

A · A person is present live exchange · no grant needed

  1. Alice → the front door. She is signed in. The front door holds one credential; she is one of many people behind it.
  2. Front door → token service. Its own client assertion, plus Alice's identity-provider token. Two identities in one request: who is calling and on whose behalf.
  3. The service verifies and folds. Her token's signature and audience against a configured trusted issuer, then her claims mapped to authority through the policy.
  4. A call token is minted. sub=alice, exec=front-door, no act, no grant, minutes to live.
  5. The call runs. She is present, so if it expires the front door mints another. Nothing durable is needed, and nothing is stored.

B · Nobody is present the case that justifies the whole design

  1. Consent, once, weeks earlier. Alice is re-authenticated — consent is a strong-auth moment — and confirms a scope, a period and limits she may only tighten.
  2. The grant is minted and stored. Her authority is folded now and that fold is the ceiling. Signed, row inserted, consent evidence recorded. Only the id comes back; the document itself never leaves.
  3. 03:00 Sunday. A schedule fires. No external input reached this frame — the trigger is the platform's own clock.
  4. Engine → token service. Its client assertion plus { grant id, trigger }. No subject token and no on-behalf-of — the grant says whose authority this is. Passing a subject token here is refused, because the only way to widen is to consent again.
  5. Seven refusals, in order. Signature verifies; not revoked; inside its period; runs remaining; the person is still active — one cached liveness lookup, which is liveness and not authority; the trigger kind is permitted; and if the grant pinned the agent's digest, the mounted catalogue still matches — otherwise the agent was re-released and this needs re-consent.
  6. Mint. Runs-used incremented atomically, token minted with cnf naming the engine, garm = scope ∩ manifest ∩ ceiling.
  7. The tool call. The receiver checks cnf against the caller identity the server placed in the subject. The tool sees sub=alice and runs its own per-record checks for her. It cannot tell this from a live call, and that is correct — the authority is hers, narrowed.
  8. The ledger. The row carries the grant and the trigger, so "why did my account do that at 3am" has a real answer: your weekly-digest grant, on the 5 October schedule.

C · A service is the principal where the design stops

  1. A batch job starts. On a schedule, or triggered by another system. There is no person anywhere in this story.
  2. Job → token service. Its client assertion. This part is solved and built: the service's identity is proven exactly as any client's is.
  3. And then nothing. There is no consenting principal, so there is no grant, no ceiling, and no fold. Authority has nowhere to come from: the claims policy maps a person's claims to authority, and a service has no such claims to map.
  4. The spec names this and declines it. "It does not let an agent act with authority no person has… an agent that must act for nobody is a different design, and the register chose not to build it."
  5. What would fill it is a service principal whose authority comes from its own registration rather than from a consent — standard enough, but it is a new source of authority, not a reuse of an existing one. That is the decision to take, not a detail to implement.

Four gaps found while researching this

1 · The presenter binding was never implemented gap

The security property is stated as a test — "a token presented by a workload other than cnf.sub is refused" — and cnf appears nowhere in the code. Not in the token service, not in the grant contract. The property that stops a model-driven decider from lifting a token is the one that does not exist.

2 · The check depends on a mechanism the spec never names gap

That same frame says to compare cnf.sub against "the connection's identity". But a receiver cannot read the connection's identity off a message — I verified the struct. So the check as written is not implementable, and the fix is not in the token at all: the caller identity has to be put in the subject by the server, via the cross-account mechanism above. Good news, in that it exists; worth knowing, in that the design assumed something it never specified.

3 · A deployment cannot limit what any call may do open · named

Caveats live on a grant, and a grant is one person's — so a caveat binds only that person's calls, and most calls carry no grant at all. "Never above €1m, whoever asks, whoever approves" cannot be expressed as a caveat, and there is nowhere else to put it either: the authority model carries clearance, compartments, verbs and tool sets, and no predicates. The spec flags this itself rather than letting a reader assume caveats cover it.

4 · Two kinds of caveat, and only one is enforceable centrally designed

"At most €500" is a predicate over one request — enforceable by whatever holds no database. "At most €500 per month" requires counting, which needs a store. So stateful caveats are forwarded to the owning tool, and only to a tool that declared it enforces that kind. Both halves have to be refusals: a grant carrying a caveat the tool never declared, and a tool that declared one and received no grant. Either half alone fails open.

What this means for sequencing

Nothing above changes the first step, and that is the useful result.

  • Transport authentication comes first, and still waits on nothing. Credentials and subject permissions establish which process is which. That is the exec identity the token binds itself to with cnf, and the server-placed caller identity the binding is checked against. It is a prerequisite for the grant model rather than an alternative to it — and it closes the hole where a misdirected message was accepted because two unrelated types both carry a string in field one.
  • A run records a grant reference and a trigger, not a principal string. The principal is derived; authority is the fold at mint time. Getting that column right the first time is the whole reason to design this before the store lands.
  • The grant store belongs to the token service, and nothing else reads it. So the engine takes a database for runs and never for grants — which keeps the one constraint that survived from the previous estate.
  • Adapt the exchange machinery; do not rewrite it. The issuer, keyring, discovery document, claims fold and client assertions exist and are tested. What is new is the grant store, the presenter binding, and a door the engine can mint through without leaving the bus.
  • Decide the service-principal question explicitly. It is the gap that looks smallest and is actually a new source of authority. It should not be discovered during implementation.

The one-line version

Short tokens are not the problem to solve — they are the mechanism. Durability belongs in a signed, revocable, countable grant that never travels; the token that travels should live for minutes and be bound to the process carrying it. That covers a person at a keyboard and an agent at 03:00 with the same machinery. It does not yet cover a service that answers to nobody.
