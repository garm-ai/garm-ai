garm-ai · deployment

Two durable engines, one bus

DBOS and Temporal are not two kinds of runner. They are two implementations of one declared kind — and a tool author cannot tell which one a deployment runs, which is the point.

Everything below the bus is reached the same way: rund resolves a name to a subject and calls it. Green is built today, terracotta is the next step, dashed is designed and not built.

The topology, and what each box keeps

Three stores, and they hold different things. rund's Postgres holds a run's public state — waiting, finished, the result, the tree. Each durable decider's store holds its own execution position, which rund never reads and has no field for. The core banking system holds the money, and is somebody else's.

trace a

A synchronous call that ends in a mainframe

payments.v1.get_balance, declared sync: { budget: 2s }. No decider loop, no run store, no runner deployed — and the budget is spent almost entirely in the last two frames.

A · garmctl call payments.v1.get_balance '{"account_id":"a-1"}'

  1. client marshals the request and sets the deadline to 2s — the declared budget, not a number the caller chose. Headers carry correlation, causation, message id, the idempotency key and traceparent.
  2. bus request on garm.run.v1.invoke.
  3. rund resolves the name in the catalogue → Sync{2s}. Refuses here if approval policy were attached to a sync tool. Creates run r1 and stores nothing — the dashed line to Postgres is not taken.
  4. rund the built-in single-step decider returns one action: call the tool. In-process, no hop.
  5. bus request on garm.tool.payments.v1.get_balance, deadline 2s, same correlation, causation now rund's message id.
  6. paymentsd natsserve unmarshals and calls your handler with a context carrying the ids and the 2s deadline.
  7. core banking the handler does the real work over HTTP, MQ or a mainframe gateway. This is where the 2s goes. A timeout here returns UNAVAILABLE, which is the one kind that tells the caller a retry is worth it.
  8. back response marshalled, replied, unmarshalled into *GetBalanceResponse. One run id was logged; nothing was persisted.

Frames 3 and 4 are the whole argument for the built-in decider. A deployed “sync runner” would add two hops and a dependency to a call that is otherwise a single round trip plus whatever the bank's system costs.

trace b

An agent whose durability belongs to Temporal

Declared agent { workflow: {…} }, therefore async. A deployment chose Temporal; the declaration does not mention it.

B · client.TriagePayment(ctx, req) → run.Ref

  1. rund resolves the name → an agent declaring workflow. Its routing table maps that kind to garm.runner.workflow.temporal — deployment config, not a declaration.
  2. rund creates run r2 in its own Postgres: RUNNING, the input, the correlation id, no parent.
  3. rund replies at once with {run_id: r2, pending}. The caller's Await is its own patience from here; giving up does not cancel anything.
  4. temporal decider starts a Temporal workflow. From now on Temporal owns where the program is — step, history, timers, signals — in its own store. rund has no field for any of it.
  5. decider → rund the workflow wants a tool. It does not call paymentsd itself: it invokes through rund, as a child run r3 with parent r2 and the same correlation id.
  6. rund and because it goes through rund, the allowlist is checked here, at call time — not only at compose. Guardrails, retries and the tree's budget apply identically to trace A's call.
  7. paymentsd → core banking frames 5 to 8 of trace A, unchanged. The tool cannot tell it was called by a workflow.
  8. decider → rund Report(r2, finished{result}) — request/reply, acknowledged. A fire-and-forget publish here would leave r2 RUNNING forever if it were dropped.
  9. rund persists SUCCEEDED, then publishes on garm.run.event.r2. Persist before publish, so no subscriber sees a state that did not survive.

Frame 5 is the load-bearing one. Because a decider's tool calls go back through rund, every uniform concern stays in one place — which is what makes two different durable engines safe to run side by side.

So migrating an estate from DBOS to Temporal touches no .proto and no tool. It is a line of rund config — and it can go agent by agent, because the routing table takes per-agent overrides.

The hazard this creates, and why the type check does not catch it

If DBOS and Temporal both register garm.runner.workflow, NATS queue-groups them and calls split randomly between two engines. Half your runs land in a store the other engine cannot read.

The reconciliation check from the spec does not see it: both report their kind as workflow, and both are correct. What catches it is coarser and has to be written down — $SRV.INFO showing two distinct service names answering one kind's subject. Hence the per-implementation subjects on the map: …workflow.dbos and …workflow.temporal cannot collide by accident, and sharing a subject becomes a deliberate act.

This corrects the spec, and the argument that was wrong

The spec decided that a decider is a pure reducer with rund owning all state, on the grounds that otherwise each decider kind would carry its own copy of guardrails, retries and budget accounting and they would diverge.

That argument is false. A decider's tool calls go through rund — frame 5 of trace B — so rund applies all three regardless of who initiated them. What a decider actually owns is only its own orchestration position, which is exactly what DBOS and Temporal exist to own. You do not adopt Temporal in order to run it statelessly.

deciderkeeps state between reportsstate travels
reactno — a pure reducerround-tripped through rund
workflow · DBOSyes, in its own Postgresnever leaves the decider
workflow · Temporalyes, in Temporal's storenever leaves the decider

One Report channel serves both, so the interface does not have to choose. rund is authoritative about a run's public state; a decider is authoritative about its execution state. Different facts, so there is no ambiguity about who to believe — and the two-store objection dissolves rather than being accepted.

What does not dissolve: a decider that dies silently still leaves a run RUNNING, and now the state needed to resume it is in a store rund cannot read. With Temporal that is Temporal's problem to solve, which is a reason to use it. With a hand-rolled decider it is ours, and the spec still names two mechanisms and picks neither.
